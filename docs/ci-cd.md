# CI в GitHub Actions

Workflow находится в `.github/workflows/ci.yml`. Файл `.gitlab-ci.yml` сохранён
как прежний черновик; GitHub Actions его не выполняет.

## Что запускается

При открытии или обновлении pull request в `main`, а также при push в `main`:

1. Параллельно выполняются интеграционные тесты, Bandit и Gitleaks.
2. Только после успеха всех трёх проверок собирается Docker-образ.
3. В pull request образ проверяется сборкой. После push в `main` образ также
   публикуется в GitHub Container Registry (GHCR).

Тег образа: `ghcr.io/<owner>/<repository>:sha-<полный commit SHA>`.
Имя автоматически переводится в нижний регистр. Тег связывает образ с конкретным
коммитом; подвижный тег `latest` не используется.

## Тестовое окружение

GitHub поднимает отдельный PostgreSQL 16 на время job и ждёт его healthcheck.
Тесты работают на Ubuntu runner с Python 3.12, а не внутри контейнера приложения.
Поэтому адрес БД — `127.0.0.1:5434`. Docker Compose для CI-тестов не требуется.
Зависимости устанавливаются Poetry 1.8.2 из `poetry.lock`.

Тестовые учётные данные относятся только к временной БД. Ключ авторизации
генерируется заново для каждого запуска. Production-секреты тестам не нужны.
Переменные окружения имеют приоритет над `tests.env`, в том числе в подпроцессе
Alembic. Миграции запускает существующая фикстура `migrated_db`.

Результаты pytest сохраняются как артефакт `test-results` на 7 дней, в том числе
при падении тестов. Ошибка любой проверки блокирует сборку и публикацию.

## Проверки безопасности

- Bandit проверяет Python-код приложения, исключая тесты. Публикацию блокируют
  находки средней и высокой серьёзности с уверенностью не ниже средней (`-ll -ii`).
  Это выбранный начальный порог; проверка не гарантирует отсутствия уязвимостей.
- Gitleaks проверяет доступную Git-историю целиком. Значения найденных секретов
  скрываются (`--redact`). Старый утёкший секрет тоже приведёт к падению job:
  его нужно отозвать и разобраться с находкой, а не отключать проверку.

Инструменты установлены только в CI и не добавлены в зависимости приложения.

## Что настроить в GitHub

1. Разрешить GitHub Actions и используемые actions в настройках репозитория
   или организации. Для job публикации workflow запрашивает `packages: write`.
2. После первого успешного запуска создать правило для ветки `main`
   (Settings → Rules → Rulesets или Branches).
3. Требовать pull request и успешные проверки `Integration tests`,
   `Python security scan`, `Secret scan`, `Build image` перед слиянием.
   Запретить обход правила прямым push для обычной работы.
4. По возможности требовать актуальность ветки перед слиянием. Обязательное
   одобрение другим человеком включать, только если есть второй участник.

Доступность правил зависит от видимости репозитория и тарифа GitHub.
Workflow сам не запрещает push: это делает правило ветки. До его включения
прямой push в `main` также запустит проверки и публикацию.

Для GHCR используется встроенный `GITHUB_TOKEN`; отдельный PAT для публикации
создавать не требуется. Если пакет с таким именем уже существует, проверьте,
что он связан с репозиторием и разрешает этому workflow запись.

Рабочий порядок:

```bash
git switch -c feature/my-change
# Изменения и локальные проверки
git add <файлы задачи>
git commit -m "Describe the change"
git push -u origin feature/my-change
# Открыть pull request в main, дождаться проверок, выполнить merge.
```

## Автоматический deploy после появления сервера

Сейчас workflow заканчивается публикацией образа. Job deploy не добавлена,
поскольку сервер и способ доступа к нему ещё не определены.

При подключении Linux-сервера с Docker Compose потребуется:

1. Подготовить сервер и production-конфигурацию с переменными БД и авторизации.
   Хранить production-секреты на сервере или в GitHub Environment `production`.
2. Добавить SSH-доступ и проверенный host key сервера в секреты GitHub.
3. Создать production Compose с `image:` вместо `build:` для приложения и
   миграций. Оба сервиса должны использовать один и тот же образ по SHA
   или digest из job сборки. Если на сервере уже есть БД, сохранить её volume.
4. Добавить job после `image`, выполняемую автоматически только для push в
   `main`. Сериализовать deploy через отдельную concurrency group.
5. На сервере скачать образ, выполнить `alembic upgrade head`, обновить приложение
   и проверить готовность HTTP API и соединение с БД. Перед этим реализовать
   endpoint готовности: сейчас отдельного такого endpoint в приложении нет.
6. Предусмотреть резервную копию БД и порядок восстановления. Возврат к старому
   образу сам по себе не отменяет миграцию схемы.

Приложение нужно запускать на сервере, а не оставлять в job GitHub Actions:
runner предназначен для временного выполнения задач pipeline.

## Проверка конфигурации

Локальная проверка YAML не заменяет запуск workflow. Полная проверка включает
pull request на GitHub, успешные job тестов и сканеров, сборку образа, а после
merge — появление пакета в GHCR с тегом нужного SHA. Локальные интеграционные
тесты запускаются через `make test` и требуют Docker с PostgreSQL.
